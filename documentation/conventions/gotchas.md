# Gotchas

Traps in this codebase that are easy to trip over and that **no test catches on its own**. Almost
every entry shares one failure mode: `npm run build` stays green while something on the page quietly
stops working.

Colour and theme traps live in [`theming-and-brand-color.md`](./theming-and-brand-color.md),
gradient and scanner traps in [`no-gradients.md`](./no-gradients.md), content and derived-fact traps
in [`content-authoring.md`](./content-authoring.md), and import-graph traps in
[`architecture-boundaries.md`](./architecture-boundaries.md).

## Fonts

The font is **self-hosted from a committed subset**, loaded with `next/font/local` in
`src/lib/fonts.ts`.

- **The `next/font` Google loader is banned anywhere under `src/`.** It hits the network on every
  build (CI and Vercel) and self-hosts the result anyway, so it only adds an external point of
  failure. The repo audits the ban with `grep -rn` for that import path over `src/`, **so no comment
  and no test may spell the path out verbatim** — a single prose hit makes the grep useless. The
  price of the ban: the `.woff2` is versioned in the repo and must be regenerated by hand when
  Montserrat is bumped (procedure in `scripts/prepare-fonts.md`).
- **Some file must `import { sans } from "@/lib/fonts"` and put `sans.variable` on the root
  element.** This is not styling sugar: the import is what pulls the module into the compiled graph.
  Without it `next/font/local` never runs — no `@font-face` is emitted, no `.woff2` lands in
  `.next`, `--font-montserrat` is declared nowhere, the page paints in the browser's default serif —
  **and the build still passes**. `find .next -iname "*.woff2"` after a build is the cheap way to
  prove the wiring survives; `src/lib/fonts.test.ts` is what guards it.
- **Declare the weight axis in full: `weight: "100 900"`.** `globals.css` sets
  `font-synthesis-weight: none`, so the browser **clamps** any weight outside the declared range
  instead of synthesising it. Under-declaring the axis silently flattens a weight rather than
  erroring. Which weights the design actually uses is decided by the typography tokens in
  `globals.css` (they stop at 600), not here.
- **The CSS variable must not be named `--font-sans`.** `next/font` declares the variable on `<html>`
  — the same element and the same specificity (0,1,0) where Tailwind emits its
  `:root { --font-sans: … }`. Which one wins would depend on CSS injection order, which Next does
  not guarantee. With a distinct name (`--font-montserrat`) and `globals.css` chaining
  `--font-sans: var(--font-montserrat, …)`, it is a chain instead of a cycle.
- **Keep the in-var fallback: `--font-sans: var(--font-montserrat, ui-sans-serif), …`.** Without the
  second argument, an undefined `--font-montserrat` invalidates the **whole** `--font-sans` value,
  reserve list included, and `<body>` inherits the initial family — Times New Roman in every
  browser. `fonts.test.ts` has a dedicated assertion for that comma.
- **`display: "swap"`, not `"optional"`.** With `optional`, many first-time visitors would never see
  Montserrat at all. With `swap`, text paints in the fallback immediately and LCP does not wait for
  the font.
- **Never hardcode the `adjustFontFallback: "Arial"` metric overrides, and never reuse another
  typeface's.** They are derived by fontkit from the actual file on disk, and they are what kills
  font CLS. Montserrat's real metrics are ascent 968, descent −251, lineGap 0, unitsPerEm 1000,
  xWidthAvg 503 — an average glyph 0.503 em wide, wider than most usual sans fallbacks. Copying
  someone else's overrides shows up as a layout jump.
- **The ~3 % residual in the fallback metrics is known and accepted.** fontkit measures the advance
  widths of the file's *default* instance, which is `wght=100` in Google's variable build (the file
  declares "Montserrat Thin" in nameID 1), so the emitted fallback is tuned slightly narrow: Next
  emits `size-adjust: 110.19%` where 113.90% would be ideal for body copy. `next/font/local` offers
  no override, and correcting it would mean `adjustFontFallback: false` plus a hand-written fallback
  `@font-face`. Do not treat the 110.19 % as a bug.
- **Two files under `src/lib/assets/fonts/` must never be deleted as "unused".**
  `OFL.txt` — Montserrat ships under the SIL Open Font License 1.1, which **requires** the licence
  text to travel with the font files; that is a legal obligation, and `fonts.test.ts` fails if it
  disappears. `Montserrat-Variable.ttf` (745 KB, the full family, not the subset) is never served to
  a browser and is not referenced from `fonts.ts`, but satori — the renderer behind `next/og` —
  cannot parse WOFF2 and has to be handed a TTF buffer; the opengraph-image route reads this file
  with `readFile` at build time.

### What `fonts.test.ts` is actually doing

- **It discovers document shells by walking `src/app/` for every `.tsx` that opens a root element**,
  and must never point at a single hardcoded path. This test has already lied once: it kept
  asserting over `src/app/layout.tsx` after the document shell had moved into the localized layout,
  and passed. The `DOCUMENT_SHELLS` list is a decision, not a cache — a new shell must fail the
  assertion, so that whoever adds it states it is intentional **and** wires the font into it.
- **`HTML_TAG` is `/<html\s[^>]*>/`, with the `\s`.** Prose in the comments above the layout
  components writes a bare `<html>`; a lazier pattern matches the comment instead of the real
  opening tag, and the test then asserts over the wrong text.
- **The `reference()` helper needs its `(?![a-z0-9-])` lookahead.** A plain substring check passes on
  a *prefix*: rename the variable to `--font-mont` and `"var(--font-mont"` still occurs inside
  `"var(--font-montserrat"`. The lookahead is what makes the chain assertions exact.
- **`LATIN_SUBSET_CEILING_BYTES` (60 000) is not redundant with the 110 000-byte Lighthouse budget.**
  The committed latin subset is 37 956 B; anything past 60 KB is no longer a latin subset —
  latin-ext, cyrillic or the full family has slipped in — which would still pass the Lighthouse
  budget while quietly doubling what every visitor downloads. The WOFF2/TrueType signature constants
  likewise catch the classic accident of renaming a `.ttf` to `.woff2`, which browsers reject and
  which costs every page its font.

## Type scale and measure

The whole type scale in `globals.css` is calibrated for Montserrat from **measured metrics**
(capsize for both families, fontTools over `Montserrat-Variable.ttf` instanced at `wght=400`), not
from intuition. Inter Regular vs Montserrat Regular: unitsPerEm 2048 vs 1000; x-height 0.5459 em vs
0.5250 em (−3.8 %); cap height 0.7275 em vs 0.7000 em (−3.8 %); mean advance over the Latin subset
0.4775 em vs 0.5030 em (+5.3 %). Those deltas are what set the body at 17 px (x-height parity with
Inter at 16 px), the measure at 36.5 rem = 584 px = 68 characters per line, and the body ratio at
1.75. **Anyone changing the font family has to redo this arithmetic.**

- **`--container-readable` stays in `rem` and must never be expressed in `ch`.** `ch` is the advance
  of the glyph "0", which in Montserrat 400 is 0.6620 em against a mean character of 0.5030 em, so
  1 ch = 1.316 real characters and the intuition "65ch = 65 characters" gives 86. Worse, `ch`
  resolves against whichever font is painted at that moment: until Montserrat loads, the Arial
  fallback with `size-adjust: 112.83%` has a "0" 5.5 % narrower, so the column would change width at
  the swap and every paragraph would re-break — exactly the CLS that `adjustFontFallback` exists to
  kill. `rem` also keeps honouring the user's browser font size.
- **The tracking ramp is measured, not arbitrary**: display −0.045, h2 −0.03, h3 −0.02, lead −0.01,
  body 0, meta +0.005, eyebrow +0.12. Montserrat is geometric and wide (the "M" is 0.955 em), so the
  ramp is monotonic with size and inverts in small text. Eyebrow is 0.12 em and not 0.14 em, which
  was too much for this family; it is 13 px at weight 600 because at 12 px uppercase the cap box is
  8.4 px, below the glanceable threshold, and Montserrat 500 frays at that size. Body tracking is an
  explicit 0 so `text-body` resets any inherited tracking.
- **At phone widths the measure cannot be met, and that is physics, not a bug in the token.** At
  360 px the usable column is 318.6 px (20.7 px gutter), i.e. 37 characters per line; at 400 px it is
  42. `--container-readable` (584 px) does not start to bite until the viewport is wider than that,
  so do not "fix" the mobile measure by shrinking the token.

## Motion

- **The classic global reduced-motion reset
  `*, *::before, *::after { animation-duration: 0.01ms !important }` is deliberately absent from
  `globals.css` and must not be added.** Its `!important` on `*` would override the 24 per-component
  reduced-motion rules the file declares one by one and leave user feedback with no signal at all,
  and it fails `tokens.test.ts`, which forbids any literal transition duration in that file.
  `prefers-reduced-motion` is answered rule by rule, not with a hammer. (`transition-delay: 0ms` is
  deliberately allowed: cancelling a delay is not declaring a duration.)
- **`tokens.test.ts` scans `globals.css` with CSS comments STRIPPED** (the `cssCode` constant) for
  its reduced-motion guards; token-value reads still use the full file. `globals.css` documents the
  removed global reset by quoting it in full inside a CSS comment, so a guard reading the raw file
  denounces the very prose explaining the prohibition. Related: the test title for the
  `transition: all` guard cannot contain that string, because the `no-restricted-syntax` block vetoes
  it in any Literal under `src/**` and a test title is a Literal — the title names the property
  instead of the utility.
- **`cubicBezier` in `src/lib/motion/tokens.ts` is hand-written on purpose.** Re-exporting it from
  `"motion/react"` pulls the framer-motion barrel into the route bundle, and `motion-utils` — where
  the function really lives — is not a declared dependency of this project.
- **One shared `IntersectionObserver`, not motion's `whileInView`.** `whileInView` creates one
  observer and one VisualElement per element; with ~30 reveals on a page that is 30 observers and 30
  motion elements, against 1 observer and 0 runtime dependencies for the shared one in
  `src/lib/motion/reveal-observer.ts`.
- **`markMotionReady()` only promotes `data-motion` "on" → "ready", never "off" → "ready".** `"off"`
  means the 3 s fail-safe in `MOTION_BOOT_SCRIPT` already fired and the content is being shown
  unanimated; promoting it back would re-hide content the visitor can already read.
- **The hidden state lives entirely in CSS, behind `html[data-motion]`; no primitive may ever write
  `opacity: 0` inline.** With JS disabled the attribute never exists and `data-reveal="hidden"`
  styles nothing; if the bundle dies, the 3 s timer flips the attribute to `"off"` and the content
  appears. An inline opacity survives that fail-safe and the content stays invisible forever.
- **`Reveal` must not be used above the fold** — its initial state is opacity 0, which would delay
  LCP until hydration. The hero uses CSS keyframes instead.
- **`Reveal`'s `--motion-reveal-index` inline style is emitted only when `step` is given and must
  never default to 0.** An inline style beats any selector, so a default of 0 pins every child of a
  `<Stagger>` to index 0 and the stagger silently stops existing.
- **Do not nest `<Reveal>` inside `<Stagger>`**: it registers a second observer per child and each
  child reveals on its own instead of the list entering as a list. `Stagger`'s direct children must
  arrive already carrying `data-reveal="hidden"` from the Server Component that renders them —
  `Stagger` must never set it, clone children or walk them, because that would stop it being a pure
  wrapper and `children` would no longer stay a server-rendered prop.
- **`CountUp` never renders the number itself.** The server already renders the final value inside
  `children`; the client only overwrites `textContent` while the animation runs. That is what keeps
  it correct with JavaScript disabled, with a dead bundle, or under `prefers-reduced-motion` — and
  the reduced-motion check must run **first**, before any observer is created, or the observer is
  installed anyway and the animation still runs. Frames write through a ref, never React state
  (~54 setState calls in 900 ms otherwise), and the counter is deliberately not a live region:
  assistive tech reads the final value, which is in the DOM from the first paint.
- **No module in the motion/scroll layer may attach a `scroll` event listener**, and layout reads
  happen once at mount, never inside a handler. The test file scans the sources for
  `addEventListener("scroll"` and for extra `new IntersectionObserver` calls.
- **Each concern gets its own observer; they cannot be shared.** An `IntersectionObserver` freezes
  `threshold` and `rootMargin` at construction: the reveal singleton is one-shot (threshold 0.15,
  rootMargin `"0px 0px -12% 0px"`) and unobserves on first hit, the scroll spy needs a
  header-derived `rootMargin` and must keep firing, and `usePassed` needs threshold 0 in both
  directions forever. What is shared is the discipline: one observer per concern, never one per
  element.
- **`useScrollSpy` reads `--header-height` with a throwaway probe element**, never with
  `getComputedStyle().getPropertyValue("--header-height")`, which returns the string `"4rem"` while
  `rootMargin` needs pixels. The probe lets the browser do the conversion, keeping
  `scroll-padding-top`, `scroll-mt-header` and this `rootMargin` derived from one token. It also
  takes **no argument**: the ids come from the `SECTION_IDS` module constant, because a caller
  passing an inline array gives the effect a new dependency identity on every render and rebuilds
  the observer each time.

## Document shells and routing

Exactly two files render a document shell: `src/app/[locale]/layout.tsx` and `src/app/not-found.tsx`.

- **`import "./globals.css"` stays in the root layout** and must not be moved into the two files that
  render `<html>`. The root 404 renders inside the root layout, not inside the localized one: if the
  stylesheet import moved, the root 404 would ship without a single rule of the design system —
  unstyled black serif on white — and the build would still pass.
- **The 404 lives at the project root with its own document shell, not at `[locale]/not-found.tsx`.**
  Verified on Next 16.3.4: `notFound()` from a `[locale]/[...rest]` catch-all returns a real 404
  status but serves the `__next_error__` shell; the translated copy only arrives in the RSC payload
  and appears after hydration, so a crawler or a visitor without JavaScript sees a blank page painted
  in the wrong theme. And `redirect()` from inside `not-found.tsx` is not an escape hatch: in Next 16
  it emits no HTTP redirect at all, it renders a 404.
- **The 404 shell deliberately duplicates `THEME_INIT_SCRIPT`** (it is outside `[locale]` and
  inherits nothing), and deliberately omits `MOTION_BOOT_SCRIPT` and the scroll sentinel (no
  `<Reveal>`, no `<Stagger>`, no header, so `html[data-motion]` would be set for nobody and the 3 s
  fail-safe would run on a page with nothing to fail safe). Without the theme script, a visitor whose
  cookie says `dark` gets a white flash and then a white 404 — exactly the failure this file exists
  to avoid. It is also what `suppressHydrationWarning` on its `<html>` is suppressing.
- **Without the motion boot script in the localized layout, `html[data-motion]` never exists**, the
  `html[data-motion="on"|"ready"] [data-reveal="hidden"]` selectors never match, and the ~30 reveals
  of the site are dead code. Content stays visible — the safe degradation — but the whole animation
  system is silently absent.
- **The two inline `<head>` scripts must not be "hardened" with a nonce or a hash.** The project's
  CSP is `script-src 'self' 'unsafe-inline'`; per CSP level 3, a nonce or hash in the same directive
  makes the browser **ignore** `'unsafe-inline'`, which would block Next's own bootstrap scripts
  along with these two. `src/app/document-shell.test.ts` asserts no inline script carries a nonce.
- **The `Errors` namespace has to be added to `NextIntlClientProvider` by hand**, on top of the three
  island namespaces `clientMessages()` returns. `src/app/[locale]/error.tsx` is a fourth browser
  consumer of `t` — a React error boundary is a class boundary, so Next requires it to be a client
  component — and its three strings live under `Errors.boundary*`. With only the island namespaces it
  renders the literal key path `'Errors.boundaryTitle'` and logs `MISSING_MESSAGE`, a failure that
  only surfaces when something else has already gone wrong.
- **Home metadata must be `generateMetadata`, not `export const metadata`**: the title and
  description are translated and a static object cannot call `getTranslations`, and exporting both
  from one file fails the build. `Meta.title` and `Meta.description` take three ICU arguments
  (`{name}`, `{role}`, `{years}`); left unresolved, next-intl reports a formatting error and both
  home pages ship the literal string `'Meta.title'` as their `<title>`. The years are always
  computed, never typed as a literal.
- **Every page under `[locale]` calls `setRequestLocale` and declares `generateStaticParams`.** A
  page that skips `setRequestLocale` turns its route dynamic in silence; nothing fails, and only the
  build output table reveals it.
- **Section ids MOVE from the `<section>` to the heading block, never get copied.** The heading block
  owns the id and the `scroll-mt-header` that compensates the fixed header, and the `<section>` keeps
  only `aria-labelledby`. Two elements with the same id is invalid HTML and the scroll spy would
  observe the wrong one. The hero is the exception and keeps its id on the `<section>`, because it
  has an `<h1>` and not a `SectionHeading`.
- **`localeDetection: false` and `localeCookie: false` in `src/i18n/routing.ts` are not
  preferences.** With detection on, the same URL returns two different documents depending on an HTTP
  header, which breaks canonicality and CDN caching; and next-intl writes `NEXT_LOCALE` even when
  detection is off, because `syncCookie()` only reads `routing.localeCookie` (see
  [`content-authoring.md`](./content-authoring.md) for why an undeclared cookie is a legal problem).
  `document-shell.test.ts` asserts the `localeCookie` line is still there.
- **`src/i18n/request.ts` fixes `timeZone`, and that is not cosmetic.** `useFormatter().dateTime()`
  runs on the server at build time and again in the browser on hydration; without a fixed zone the
  two runs use different offsets and React reports a hydration mismatch on the legal pages, whose
  only formatted value is a date.
- **An unknown locale falls back to the default in `request.ts` and must never be rejected with
  `notFound()` there.** That function also runs for `app/not-found.tsx`, where `requestLocale` is
  undefined by design, so `notFound()` would make the root 404 recurse instead of rendering. The
  fallback cannot cause a silent wrong-language page: the proxy already 404s unknown prefixes and
  `app/[locale]/layout.tsx` rejects them.

### What `document-shell.test.ts` can and cannot prove

It stands in for a deferred Playwright spec, and its wiring assertions **grep the `.tsx` source as
text** instead of importing it — both shells are async Server Components pulling in
`next/font/local`, a build-time transform that throws outside the Next compiler, so grepping is the
only option for a unit test. The chain is worth asserting because the build stays green while the
theme stops persisting, the reveals become dead code, or the header stops reacting.

Three claims stay **manual checks**, because a Vitest run in the `node` environment cannot observe a
real cookie jar (what it proves instead is that no line of `src/` is capable of writing a cookie):
that a first load of `/` and `/es` really arrives with an empty jar; that one click on the theme
toggle lands exactly one `Set-Cookie`; and that a `theme=dark` cookie paints no flash of light on a
throttled connection.

## Build, headers and tooling

- **The CSP keeps `script-src 'unsafe-inline'` instead of switching to a nonce.** A nonce-based CSP
  forces every route to render dynamically, which destroys full static generation for the whole site.
- **`'unsafe-eval'` is added to `script-src` outside production only.** The Turbopack runtime and
  React Refresh evaluate hot modules; without it `next dev` starts with HMR silently blocked by the
  site's own CSP.
- **`Strict-Transport-Security` is never emitted outside production.** On localhost HSTS does nothing
  useful, and if any local service later shares the hostname over plain HTTP the browser refuses it
  for the full max-age (two years).
- **`/cv/:path*` is served with `X-Robots-Tag: noindex, noarchive` and a short `s-maxage`** rather
  than an immutable cache: the CV PDF carries a personal phone number, so the site is meant to rank
  but the PDF is not — and the PDF is regenerated from time to time, so it must revalidate rather
  than be frozen.
- **`SITE_INDEXABLE` is not dead configuration.** It is the explicit override that makes a build
  indexable where `VERCEL_ENV` does not exist — the Docker image, and any local build audited with
  `npx lhci autorun`. Deleting it as unused makes those builds ship `noindex`.
- **Port 3200 is declared once, in the `dev` and `start` scripts of `package.json`; nothing else may
  pass `--port`.** `npm run start -- --port 3112` expands to `next start --port 3200 --port 3112`,
  and which value wins is left to the argument parser.
- **The E2E run sets `TRUST_PROXY=1` and a fixed `RATE_LIMIT_SALT`, which production leaves unset.**
  It lets `contact.spec.ts` present a distinct client address per test so the contact form's
  three-per-hour bucket never couples two tests. In production, trusting `X-Forwarded-For` behind a
  bare published port lets a client forge the header and walk around the rate limit.
- **`vite-tsconfig-paths` is mandatory in `vitest.config.ts`, and Playwright specs stay out of the
  Vitest `include` glob.** Without the plugin, no test that imports the `@/` alias can even load;
  with a wider glob, Vitest picks up `tests/e2e/*.spec.ts` and fails on Playwright's API.

### Typecheck and lint traps in tests and scripts

- **`noUncheckedIndexedAccess` is on**, so `array[i]` is `T | undefined`. It was verified not to
  affect `Record<Locale, string>` lookups, so locale maps keep their narrow types. Consequence in
  `scripts/check-contrast.ts`: the linear RGB tuple is built as an explicit three-element literal,
  not `as unknown as LinearRgb` over `.map()` — `.map()` yields `number[]`, and the double assertion
  would silence exactly the check the flag exists to perform.
- **`eslint .` lints `scripts/` and test files too, and `@stylistic/wrap-regex` requires parentheses
  around a regex literal used as the object of a member expression.** That is why regexes are
  extracted to module constants (`NEUTRAL_FOLLOWS_BRAND` and `PRIMITIVE` in `check-contrast.ts`, the
  patterns in `primitives.test.ts`) instead of written inline as `/re/.test(x)`.
- **`Reveal` renders its dynamic tag as JSX with a `ref as Ref<never>` cast, not with
  `createElement`.** Passing a `ref` inside the props object of `createElement` trips
  `react-hooks/refs` in `eslint-config-next@16.3.4`, and `npm run lint --max-warnings 0` is the gate.
  The cast is the price of accepting a closed union of nine tags; the alternative is a nine-branch
  switch. (The union is closed on purpose: `as: ElementType` types the props loosely and lets invalid
  tag/prop combinations through.)
